# Project brief: ECMWF chart viewer

(Saved verbatim from the owner's brief, without section 0 "How to work with me", which is summarised in `CLAUDE.md`.)

## 1. Product (decided)
An Android app (APK, later) that views numerical-model weather charts in the style of the KMA "예상일기도" viewer. Charts are PRE-RENDERED PNGs generated by GitHub Actions from ECMWF open data and served as static files by GitHub Pages. The app only downloads PNGs and a JSON manifest. No other backend (no Cloudflare, no server). ECMWF IFS first; KIM is out of scope.

## 2. Data source
- ECMWF IFS open data, 0.25 deg, GRIB2. Licence CC-BY-4.0 + ECMWF Terms of Use: attribution is mandatory. Add a NOTICE file and an on-chart credit. ECMWF's own example wording: "Adapted from 'ECMWF IFS 15-day Forecast Data' by ECMWF, licensed under CC BY 4.0, available at https://data.ecmwf.int/forecasts/". Check the Terms of Use for the exact wording and keep a "modified data" note.
- Checked on 2026-11-14 at https://www.ecmwf.int/node/28188 (re-check):
  - Steps: 00/12Z runs: 0-144 by 3, then 150-360 by 6 (we use up to 240 h). 06/18Z runs: 0-144 by 3 (NOT 90 h).
  - Pressure levels include 925, 850, 700, 500, 300, 200 hPa. Params: gh, t, u, v, q, r (IFS only), msl, sp, tp. Units are NOT stated on that page: read them from GRIB metadata.
  - The portal is "limited to between 500 and 2000 simultaneous connections"; ECMWF recommends the AWS/Azure/Google mirrors. The portal keeps only the latest 12 runs. Mirror retention is not stated (a forum answer says AWS keeps older runs).
  - 0.1 deg data exists since 2026-10-20 (separate -sfc/-pl files, ~2 h after 0.25 deg). That is Stage 3 only, but keep resolution a config parameter.
- Use the official `ecmwf-opendata` Python client (`Client(source="ecmwf"|"aws"|"azure"|"google")`; `retrieve()` downloads only the requested fields; `latest()` returns the newest matching run). Check its current docs. Fields are global; there is no server-side crop, so crop at render time.
- Fields per step (30 total): surface msl, sp, tp; 925 and 850: gh,t,u,v,q; 700: gh,t,u,v,r; 500/300/200: gh,t,u,v. (sp is used to mask underground points on 925/850.)
- Raw size upper bound is about 41 MB per step: 00/12Z run (65 steps up to 240 h) about 2.7 GB, 06/18Z run (49 steps) about 2.0 GB. The runner disk is 14 GB, so process step by step and delete GRIB files as you go.

## 3. Published steps and images
- Publish images only for valid times on the 6-hourly grid (00/06/12/18 UTC): 00/12Z runs steps 0-240 by 6 (41 steps), 06/18Z runs steps 0-144 by 6 (25 steps).
- Precipitation chart at such a valid time = accumulation over the preceding 3 h (forecast hour <= 144) or 6 h (> 144): tp(step) - tp(step-3 or -6). So tp (only) needs the intermediate 3-hourly steps. Whether tp is cumulative from step 0, and its unit, are UNVERIFIED.
- 14 images per published step, so 574 images per 00/12Z run and 350 per 06/18Z run.

## 4. Domains and charts
- Default domain: 25-48N, 110-140E, plate carree, 0.25 deg. The 500 hPa chart ONLY also gets a wide domain 10-50N, 100-180E.

| id | content |
|---|---|
| msl | mean sea-level pressure contours (hPa) + H/L markers with values |
| tp | 3 h (6 h after +144 h) accumulated precipitation, shaded |
| gz925, gz850, gz700, gz500, gz300, gz200 | gh black labelled contours (gpm) + temperature (deg C) + wind barbs (kt) |
| rh700 | relative humidity shading (+ gh contours) |
| mfc925, mfc850 | moisture flux convergence (section 6) |
| wpsh500 | transparent PNG overlay, same extent and size as gz500 (section 5) |
| gz500_wide, wpsh500_wide | wide-domain versions |

- Temperature style is undecided: for gz500 only, render two variants for me to choose from. A: temperature as colour fill with a right-hand colour bar. B: dashed isotherms.
- Dropped for now: vorticity, equivalent potential temperature, a fixed 5880 line. (Vorticity and theta-e could be recomputed later from the same u/v/t/q.)

## 5. 500 hPa red line (west Pacific subtropical high edge)
- Red contour at the level (H - 50 gpm), where H is the highest of the closed local maxima of 500 hPa height inside a west-Pacific search box. KMA has no documented definition; this is a WORKING definition to be tuned on real data.
- Draft rule: search box about 10-40N, 120-180E (west edge raised to 120E to avoid Indochina/South China Sea highs). Candidate = local maximum within a +/-5 deg window, excluding candidates within 2 deg of the box edge. H = max over candidates. If there is none: "no centre" (no line; the legend says so). Keep all parameters in config.
- Draw the contour unfiltered (closed loops around lows included), as a separate transparent PNG so the app can toggle it. Each frame's legend shows H and H-50 (or "no centre").

## 6. Moisture flux convergence charts (850 and 925 hPa)
- Title style: "850hPa Moisture Flux(m/s) and Convergence(E-9/s)".
- Shading: only convergence = negative values of div(qV) in 1e-9 s^-1 (q in kg/kg, V in m/s). Colour bar 0 to -50 in steps of 5, light lavender to purple to cyan to blue. Black labelled contours at 0, +/-10, +/-20 ..., with only positive (divergence) contour lines drawn and no fill (interval 5 or 10: make it config). Red vectors of qV, length proportional to |qV|, subsampled every 2-3 grid points, with a reference-vector key. Dashed graticule with labels (e.g. 125E, 130E, 36N, 40N).
- Compute with spherical divergence (1/(a cos(lat))), light smoothing, and mask points where the level pressure exceeds sp.
- The sign convention and scaling are my reading of a KMA reference chart: UNVERIFIED. Sanity-check the magnitudes against the colour-bar range.

## 7. Common chart style, manifest, hosting
- Style (from the KMA/KIM reference charts): title top-left, model label "ECMWF IFS 0.25deg" + CC-BY credit, footer with a VALID line at the left (UTC in red, KST in black) and a TIME line at the right (run time + forecast hour), colour bar on the right, light coastlines/borders. Keep all styling in one config file.
- Manifest: a versioned `index.json` (`schema_version`). It must let the app (a) list charts and levels; (b) for a fixed chart + valid time, list every run that has a frame, so a future "past-run playback" can play oldest to newest with the newest emphasized; (c) show H and H-50 per 500 hPa frame. Keep it small.
- Hosting: GitHub Pages only, deployed from Actions (I will enable Pages with source = GitHub Actions when you tell me). The published site must stay <= 1 GB and deploy within the 10-minute timeout. Pages replaces the whole site on each deploy, so the pipeline must restore the previous site, prune the oldest run FIRST, add the new run, then deploy. If the cache is lost, re-render from a cloud mirror.
- Retention target: 10 runs (2.5 days) of 6-hourly-grid images = 5x574 + 5x350 = 4,620 images. That reaches 1 GB at about 216 KB average per PNG, so REQUIRE a measured average <= 190 KB (about 0.88 GB). Otherwise fall back to 8 runs (2 days, 3,696 images, 1 GB at about 271 KB). Levers: PNG8/palette quantization, WebP (the future app is an Android WebView).
- Scheduling (later): GitHub cron is best-effort (late or skipped; disabled after 60 days without repo activity). Design the pipeline to be idempotent: a poll job (cron + workflow_dispatch) renders any complete run not yet rendered, plus a keepalive.
- Later stages, do NOT build now: Stage 1 full renderer + Pages deploy. Stage 2 APK (Capacitor WebView wrapper built in Actions; the signing keystore comes from Actions secrets that I will provide; never generate or commit a keystore) and the app UI (mint/teal palette, large readable text, rounded corners, minimal mobile margins, long explanations collapsed by default, Korean strings). Stage 3 0.1 deg and KIM.
- Future past-run viewer: a toggle on a chart opens a window that plays that chart's frames across runs at a FIXED valid time, past to present, newest emphasized, each frame labelled with its run time (and H-50 for 500 hPa). With 10 retained runs expect about 10 frames up to +90 h (newest run), 7 at +120 h, 5 at +144 to +180 h, 1 at +240 h.
